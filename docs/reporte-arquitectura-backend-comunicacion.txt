REPORTE DE ARQUITECTURA, BACKEND Y COMUNICACION DEL SISTEMA

Sistema: Gestion de articulos cientificos
Tecnologias principales: ASP.NET Core / .NET 9, Blazor WebAssembly, SQL Server, Entity Framework Core, JWT, Docker

1. ARQUITECTURA GENERAL

El sistema esta construido bajo una arquitectura modular cliente-servidor. La solucion se divide en tres proyectos principales:

- tesisproject.frontend: interfaz de usuario desarrollada en Blazor WebAssembly.
- tesisproject.backend: API REST desarrollada en ASP.NET Core / .NET 9.
- tesisproject.shared: proyecto compartido que contiene DTOs y contratos usados por frontend y backend.

La arquitectura general funciona de la siguiente forma:

Usuario
  -> Frontend Blazor WebAssembly
  -> API Backend ASP.NET Core
  -> Servicios de negocio
  -> Entity Framework Core
  -> SQL Server / Data Warehouse

Esta separacion permite que la interfaz de usuario, la logica de negocio y la persistencia de datos se mantengan organizadas, independientes y escalables.

2. COMUNICACION ENTRE FRONTEND Y BACKEND

El frontend se comunica con el backend mediante peticiones HTTP hacia endpoints REST.

Los principales metodos utilizados son:

- GET: consultar informacion.
- POST: crear, enviar o procesar informacion.
- PUT/PATCH: actualizar informacion cuando corresponde.
- DELETE: eliminar registros cuando el modulo lo permite.
- Descarga de binarios: para PDF, Excel, CSV o ZIP.

El flujo general de comunicacion es:

Pagina Blazor
  -> Cliente HTTP del frontend
  -> ApiClient
  -> Endpoint del backend
  -> Controller
  -> Service
  -> DbContext / API externa / Data Warehouse
  -> DTO de respuesta
  -> Interfaz de usuario

El frontend no accede directamente a la base de datos. Toda accion operativa pasa por el backend, lo cual permite mantener control de seguridad, validacion, permisos y trazabilidad.

3. USO DEL PROYECTO SHARED

El proyecto tesisproject.shared contiene los DTOs que comparten frontend y backend. Esto permite que ambos lados usen las mismas estructuras de datos para solicitudes y respuestas.

Ejemplos:

- RegisterArticleAggregateRequest
- InstitutionalReportingDashboardDto
- ExternalApiQueryRequest
- BulkImportActionResultDto
- WorkflowReviewDto

Ventajas:

- Evita duplicar modelos entre frontend y backend.
- Reduce errores de compatibilidad.
- Mantiene contratos tipados.
- Facilita cambios controlados en los datos enviados por API.

4. ESTRUCTURA MODULAR DEL BACKEND

El backend esta organizado por carpetas y modulos funcionales:

- Configuration: configuracion de servicios, pipeline, CORS, autenticacion y validaciones iniciales.
- Controllers: puntos de entrada HTTP organizados por modulos.
- Data: modelo transaccional OLTP y entidades del sistema.
- DataWarehouse: modelo dimensional y entidades del Data Warehouse.
- Reporting: contexto y modelos de lectura para reportería BI.
- Services: logica de negocio organizada por modulos.
- Identity: usuarios, roles, politicas y JWT.
- Options: opciones de configuracion, como APIs externas e identidad institucional.
- Mapping: conversiones entre entidades y DTOs.
- Errors: excepciones controladas.

5. CONTROLADORES

Los controladores reciben las solicitudes HTTP desde el frontend. Su responsabilidad principal es validar la entrada basica, aplicar autorizacion y delegar la logica al servicio correspondiente.

Controladores principales:

- AuthController: inicio de sesion y autenticacion.
- IdentityAdministrationController: gestion de usuarios y roles.
- ArticlesController: listado y gestion de articulos.
- ArticleRegistrationController: registro individual y envio a revision.
- BulkImportController: carga masiva y staging.
- RegistrationMatricesController: matriz maestra de registro.
- WorkflowController: flujo de revision institucional.
- ConfigurationController: formularios, campos y catalogos.
- ExternalApiExplorerController: integracion con APIs externas.
- ReportingController: dashboards, PDF, Excel, ETL y metricas.
- IntelligenceController: predicciones, recomendaciones y entrenamiento IA.

Ejemplo de flujo:

POST api/articles/aggregate/submit-for-review
  -> ArticleRegistrationController
  -> ArticleRegistrationService
  -> BulkImportService / WorkflowService
  -> AppDbContext

Servicios principales:

- ArticleRegistrationService: registro individual de articulos y envio a revision.
- ArticleAggregatePersistenceService: persistencia del agregado articulo, participantes, revista e indexaciones.
- ArticlesService: consulta, listado y detalle de articulos.
- BulkImportService: staging, validacion, carga masiva y procesamiento.
- RegistrationMatrixService: matriz maestra, filas, columnas y celdas.
- WorkflowService: toma de caso, validacion, devoluciones y procesamiento final.
- ConfigurationFormsService: formularios dinamicos, campos, catalogos y validaciones.
- ExternalApiExplorerService: consulta de APIs externas como Scopus, Crossref, OpenAlex y Semantic Scholar.
- InstitutionalReportingService: reportería, KPIs, PDF, Excel, dataset y ETL.
- InstitutionalIntelligenceService: predicciones, recomendaciones y entrenamiento IA.
- IdentityAuthService: autenticacion de usuarios.

- ReportingRefreshQueue: refresco automatico de reportería en segundo plano.

7. FLUJO CONTROLLER - SERVICE - DBCONTEXT

El backend sigue una estructura clara:

Controller
  -> Service
  -> DbContext
  -> SQL Server

El controller no contiene logica pesada. El service concentra reglas de negocio. El DbContext se encarga del acceso a datos.

Ejemplo:

ArticleRegistrationController
  -> ArticleRegistrationService
  -> ArticleAggregatePersistenceService
  -> AppDbContext
  -> TesisDB_Extensible

14. POR QUE NO SE USA UNIT OF WORK PROPIO

El sistema no implementa un patron Unit of Work propio porque Entity Framework Core ya proporciona esta funcionalidad mediante DbContext.

En EF Core:

DbContext = Unit of Work + Repository

DbContext permite:

- Rastrear cambios en entidades.
- Agrupar operaciones antes de guardar.
- Ejecutar SaveChanges como unidad transaccional.
- Manejar transacciones implicitas.
- Crear transacciones explicitas cuando son necesarias.
- Consultar entidades mediante DbSet.

Agregar un UnitOfWork adicional podria duplicar responsabilidades, aumentar la complejidad y reducir la expresividad de EF Core sin aportar un beneficio significativo para este caso.

15. POR QUE NO SE USAN REPOSITORIOS GENERICOS

El sistema no utiliza repositorios genericos porque los servicios necesitan consultas especificas y reglas propias por modulo.

Ejemplos:

- Workflow requiere validar estados, etapas, responsables y devoluciones.
- BulkImport necesita validar filas, campos dinamicos, errores y procesamiento.
- Reporting necesita consultas analiticas y vistas del DW.
- DynamicForms maneja formularios activos, campos visibles, requeridos y editables.
- Intelligence consume series temporales y datos agregados.

Un repositorio generico podria limitar la capacidad de expresar consultas LINQ complejas y obligaria a crear capas adicionales innecesarias.

En lugar de repositorios genericos, el sistema usa servicios de dominio especializados.

22. MANEJO DE ERRORES

El backend devuelve errores controlados cuando es posible. El frontend cuenta con un mapeador de errores para convertir mensajes tecnicos en mensajes entendibles para el usuario.

Esto evita mostrar errores como:

- SqlException.
- Foreign key constraint.
- StackTrace.
- InternalServerError.

Y permite mostrar mensajes como:

- Revisa los campos obligatorios.
- No tienes permisos para realizar esta accion.
- La operacion tardo mas de lo esperado.
- Actualiza la informacion e intenta nuevamente.

24. JUSTIFICACION TECNICA

La arquitectura aplicada es adecuada porque:

- Separa frontend y backend.
- Centraliza reglas de negocio en servicios.
- Usa DTOs compartidos.
- Usa EF Core como persistencia y unidad de trabajo.
- Separa operaciones OLTP de analisis OLAP.
- Permite seguridad por roles.
- Soporta formularios dinamicos.
- Permite carga masiva controlada mediante staging.

25. TEXTO SUGERIDO PARA TESIS

El sistema fue desarrollado bajo una arquitectura modular cliente-servidor, compuesta por un frontend en Blazor WebAssembly, un backend en ASP.NET Core y un proyecto compartido de contratos DTO. La comunicacion entre frontend y backend se realiza mediante servicios HTTP que consumen endpoints REST protegidos con autenticacion JWT y politicas de autorizacion por roles. En el backend se aplico una separacion por capas, donde los controladores reciben las solicitudes, los servicios concentran la logica de negocio y Entity Framework Core gestiona la persistencia hacia SQL Server.

No se implemento un patron Unit of Work adicional debido a que el DbContext de Entity Framework Core ya cumple esa responsabilidad, administrando el seguimiento de entidades, transacciones y confirmacion de cambios mediante SaveChanges. Asimismo, se prescindio de repositorios genericos para mantener consultas especificas y expresivas por modulo, necesarias en procesos como workflow, staging, reportería, formularios dinamicos e inteligencia artificial.

La arquitectura diferencia el modelo transaccional OLTP, usado para registrar y validar informacion operativa, del modelo analitico OLAP, utilizado para reportería BI, KPIs e inteligencia artificial. Esta separacion permite que las consultas analiticas se ejecuten sobre un Data Warehouse sin afectar directamente las operaciones diarias del sistema. En conjunto, la arquitectura propuesta favorece mantenibilidad, escalabilidad, seguridad, trazabilidad y soporte para analisis institucional.
